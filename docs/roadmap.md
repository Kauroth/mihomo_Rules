# 设计说明

记录几个方向性的决定，免得过几个月自己忘了为什么这么做。

## 为什么不用 geosite / geoip

现在主分支走 rule-provider，不产出 `geosite.dat` / `geoip.dat`。原因有三条：

**表达力。** geosite 只支持 domain、full、keyword、regexp 四种域名规则，装不了进程名、端口、IP-CIDR。要混装只能改用 classical 类型的规则集。而规则集这边 `behavior: classical` 什么都能放。

**更新粒度。** geosite 是一份全量文件，任何一个分类变了客户端就要重下整份。规则集是每个分类一个文件，KB 级，各有各的 `interval`。

**分类命名。** geosite 的分类名由生成数据的那一方定，客户端只能跟着用。规则集的文件名就是分类名，随便改。

真要走 geodata 也不难，上游的数据目录支持 `include:` 聚合、`@属性` 切子集、`&affiliation` 一处维护多处出现，装个 Go 就能自己生成。只是同样的数据在规则集这边引一遍就行，没必要多养一套工具链。

## geosite.dat 的一个固有限制

自己拼出来的 geosite.dat 里属性一定是空的，`@cn`、`@ads` 都不会有。

原因是构造性的：这类数据集的常见来源是 Clash 格式的列表，而 Clash 的三种写法（`DOMAIN,` / `DOMAIN-SUFFIX,` / `DOMAIN-KEYWORD,`）里没有地方放属性字段。属性只有从域名数据集的原始格式生成时才存在，所以对应的做法是把 `apple@cn` 拆成独立的 `apple-cn` 分类。

推论：客户端里写 `GEOSITE,apple@cn` 这种行为，在那种 dat 上匹配不到任何东西，而且不报错。改用规则集之后这个问题不存在，分类名本身就承担了属性的作用。

## 已完成

- 纯文本源编译成 `.mrs`，文本版一起发布
- 非法行和 panic 都会让构建失败
- `sources/` 声明式拉取：补上游缺的分类、按属性切子集、去冗余
- CI 每天 03:00 自动重建并推 `dist` 分支
- mrs 跨小版本双向可读（v1.19.33 ⇄ v1.19.12 实测命中一致）
- 一手源自采：`rir:`（RIR 委派记录）/ `asnfile:`（iptoasn 离线表）/ `ct:`（CT 日志）三个前缀，
  IP 侧不再依赖 ispip、gaoyifan 这类第三方聚合；`!opt` 标记让交叉源挂了也不影响构建
- 平台 IP 段：现在 9 个 ipcidr 分类，netflix / facebook / oracle / steam 都按 AS 反查
- 质量守门（前两项）：条数环比（突降突增都拦）+ 属性回归（`@属性` 过滤失效就拦），
  见 `scripts/check-regression.py`；基准存 `baseline.json`，只有全部通过才更新
- 上游快照：每次构建把 `.cache/` 打包成 artifact 留 14 天，带 MANIFEST 可还原

## 待做

**sing-box 输出。** 同一份文本再编译一份 `.json` + `.srs`。麻烦的地方在语义映射：`.x`（仅子域）和 `*.x`（仅一级子域）在 sing-box 里没有对应写法，只能退化成 regex。所以有个前置约束——本仓库的 domain 列表只允许写 `x` 和 `+.x` 两种形式，其余禁用，用构建脚本强制。这样两个内核的行为才对得上。

**命中回归。** 固定一批测试域名（各分类各挑几个，带正反例），编译后用 mihomo 实跑一遍断言命中。
比条数环比更贴近实际效果——条数没变但规则写错了，只有这个能发现。sing-box 那半等它有产出了再说。

**`ct:` 的实际增益。** 目前 `ct:` 对产物是零贡献：枚举出的子域全被已有的 `+.主域` 吸收了
（openai 实测 188 条，净增 0）。它真正能发力的场景是「v2fly 没有对应分类」或
「服务域挂在不同顶级域下」，得先找到这样的分类才有意义。按组织名查（crt.sh 的 `?O=`）
可能是个方向，但 crt.sh 对这类查询不稳定，还没验证。
